# nb_mesh 发现协议：看得懂的设计说明

> 这份文档写给"不想读代码，但要把架构讲清楚 / 要判断能不能上线"的人。
> 报文细节、状态机、实测数据的更精确版本在 [mesh-discovery.md](mesh-discovery.md)。

---

## 0. 一句话

**每个节点每隔约 1 秒往一个组播地址扔一个 26 字节的小包，包里写着"我是谁、我在哪、
我能干什么"。所有人都在听，听到就记在小本本上；要调谁，翻开小本本按"能力"查一下
就能拿到 IP 和端口。没有握手、没有服务器、没有"你去拉一下我的服务列表"。**

---

## 1. 为什么不用"拉服务列表"

你之前担心的问题是对的：如果每次上线都去问邻居"你都提供哪些服务"，那 N 个节点
就是 N×N 次交互——1000 个节点就是上百万次握手，网络直接堵死。

所以这里做了一个关键取舍：

| 做法 | 一次交互能传达的信息 | 规模变大时 |
| --- | --- | --- |
| 拉服务列表（名字一批一批传） | 几百字节，内容任意 | N² 次请求，爆炸 |
| **只传一个 32 位"能力位图"** | 32 个服务的有/无 | **恒定 26 字节，不随服务数量涨** |

代价是：**服务在编译期就要定好编号**（哪个 bit 代表哪个服务）。对无人机编队这种
"服务集合基本固定"的场景，这个代价是划算的——换来的是零握手。

---

## 2. 报文长什么样

**26 字节，定长，没有 JSON/文本，所有多字节字段一律大端（网络序）。**

```
偏移  长度  字段            说明
 0     2    magic          固定 0x5A43（字符 'Z','C'）。不是本协议的数据报直接丢
 2     1    msg_type       1=JOIN(我刚上线) 2=HEARTBEAT(我还活着) 3=LEAVE(我走了)
 3     1    reserved       恒为 0，留给以后扩展
 4     4    formation_id   编队号。跟我不是一个编队的包，直接丢（这是"隔离"）
 8     8    node_id        节点唯一 ID。跟我自己一样就丢（组播会回环到自己）
16     4    real_ip        我的 IPv4。填 0 表示"你看数据报的源地址就行"
20     2    rpc_port       我的 RPC 端口（所有服务共用一个端口）
22     4    service_mask   32 位能力位图，见第 4 节
```

### 2.1 为什么是这几个字段

- **ip 和端口都在包里**：这就是"程序 A 不知道程序 B 的 IP 也能调用"的根本原因。
  客户端不配置任何对端地址，IP 是从包里学来的。
- **只有一个 rpc_port**：约定"一个节点只开一个 RPC 端口，服务靠位图区分"。
  这样 26 字节就够，不用传一串 URL。
- **没有 CRC**：26 字节定长 + UDP 自带校验和 + 全部字段严格校验，坏包最坏结果是
  多认一个 1.5 秒后自动过期的邻居，不会把表搞乱。
- **没有版本号**：magic 里已经隐含协议身份；真要升级协议，换 magic 更干脆
  （新旧版本互相直接丢弃，不会误解析）。
- **没有序号**：同一节点重启后 IP 变了，新心跳会直接覆盖旧记录；不需要靠序号
  判新旧。代价是理论上 1.5 秒租约窗口内的乱序包可能短暂盖错，随后立刻被下一次
  心跳纠正。

### 2.2 收到包之后要过 6 道关（任何一道不过就丢，不做"尽力解析"）

1. 长度必须**正好** 26 字节；
2. magic 对；
3. msg_type 只能是 1/2/3；
4. `formation_id` 必须和我一样（**编队隔离**）；
5. `node_id` 不能等于我自己（组播会把自己发的包也收回来）；
6. `node_id` 不能是 0。

## 3. 交互时序

### 3.1 节点上电

```
节点 A 上电
  ├─ 创建 socket，绑定发现端口（SO_REUSEADDR，不开 SO_REUSEPORT）
  ├─ 加入组播组（默认由编队号推导，例如编队 7 -> 239.255.x.y）
  └─ 立刻连发 3 个 JOIN，间隔 50 ms      ← "Fast-Join"：不用等 1 秒心跳
       ↓
     同编队的 B、C、D 收到，各自在小本本里记下 A：ip / rpc_port / 服务位图
       ↓
     网络里其它节点也在听，所以 A 的第一次心跳没到之前，大家就已经认识它了
```

**为什么要连发 3 次**：单个 UDP 包可能丢，连发 3 次（150 ms 内）能把"新节点被看见"
的成功率拉满，同时不至于造成流量压力。

### 3.2 稳态：心跳

```
每个节点：  每隔 heartbeat(默认 1000ms) + 随机抖动(0~400ms)  发一个 HEARTBEAT
每个节点：  每隔 200ms 扫一遍小本本，超过 lease(默认 1500ms) 没心跳的删掉
```

**抖动是重点**：1000 个节点如果同时上电、同时发包，会出现"同一毫秒内 1000 个包
一起到交换机"的尖峰。加了随机抖动后，发包时间被摊平到 1000ms 的窗口里，
任何时刻都只有少量包在飞。

### 3.3 一次调用（核心链路）

```
程序 A 想调用 service_b.method_b
   │
   ├─ 1. 查静态路由（配置里写死的 route）     命中 -> 直接发
   ├─ 2. 查本地 registry（进程内注册的）      命中 -> 直接发
   ├─ 3. 查发现层（本文档这套）：
   │      服务名 "service_b"
   │        ↓（怎么变 bit 见第 4 节）
   │      bit = 1 << 9
   │        ↓
   │      邻居表里找"谁的位图里有 bit 9"       ← O(1)，不是遍历所有邻居
   │        ↓
   │      拿到 ip=192.168.0.2, rpc_port=8080
   │        ↓
   │      组装 endpoint，直接发 RPC 请求
   └─ 4. 都没有 -> 返回 NOTFOUND（明确失败，不会傻等超时）
```

**关键点**：第 3 步这一步是**纯本地查表**，不发任何网络包。所以哪怕 5000 个节点，
一次调用的寻址开销也只有 0.5 微秒左右（实测 0.44~0.46 μs）。

### 3.4 节点下线

```
正常退出：  发一个 LEAVE          -> 邻居立刻删掉（不用等 1.5 秒）
掉电/断网：  1.5 秒没有心跳       -> 清扫时删掉
```

删掉之后，下一次寻址就返回 `NOTFOUND`，调用方立刻知道"这个服务现在没人提供"，
而不是等到 RPC 超时才失败。

### 3.5 组播不可用时

如果环境不允许组播（某些云环境/跨网段），可以配 `group = ""`，改用**定向单播**：
在配置里列几个对端地址（`peers`），心跳就只发给这些地址。功能一样，只是需要人工
维护"发给谁"的列表。

## 4. 服务表：怎么定义、怎么共享

这是整个方案里**唯一需要人工约定**的部分，也是唯一容易踩坑的地方。

### 4.1 三套机制，以及"RPC 路径实际用哪一套"

先说结论，避免踩坑：

| 机制 | 谁在用 | 说明 |
| --- | --- | --- |
| **共享服务表**（`NB_SERVICE_DEFINE`） | **RPC 应用（推荐）** | 服务 ID 直接当 bit 号，两端零碰撞 |
| **编译期位图宏**（`mesh_services.h`） | 直接调 `nb_mesh_*` API 的代码 | RPC 适配层**不读**它，见下面的说明 |
| **服务名哈希**（兜底） | 没装表的程序 | 同一个名字算同一个 bit，但可能撞位 |

#### 方式一：共享服务表（RPC 应用就该用这个）

用 `nb_service_table.h` 的宏声明"服务名 + 数字 ID"，**客户端与服务端包含同一份头**
（仓库里的完整例子：`examples/01_rpc/service_table.h`）：

```c
/* service_table.h —— 两端共同包含 */
#include <nb/rpc/service_table.h>

NB_SERVICE_DEFINE(echo_table, 0u, "EchoService",
    NB_SERVICE_METHOD(1u, "echo"));
```

然后在建节点前装上（推荐随配置一起装）：

```c
nb_node_config_default(&cfg);
cfg.rpc.service_table = &echo_table;   /* 发现层：服务 ID 0 -> bit 0 */
nb_node_create(&cfg, &node);
```

发现层的映射规则（`src/rpc/discovery/discovery.c`）：

```
服务名 -> 服务表里的数字 ID（必须 < 32） -> bit = 1 << ID
```

所以：
- **服务 ID 必须 < 32**（心跳位图 32 位）；
- 同名不同 ID 在装表时就会报错，不会带到线上；
- 两端必须装**同一份**表，否则算出的 bit 不同。

#### 方式二：编译期位图宏（只有直接调 nb_mesh 时生效）

`include/nb/mesh_services.h` 里把能力按子系统分组写死 bit：

```c
#define NB_SERVICE_CORE_FCS     (1U << 0)   // 飞控
#define NB_SERVICE_CORE_HEALTH  (1U << 1)   // 健康检查
#define NB_SERVICE_SENSE_SLAM   (1U << 8)   // SLAM
#define NB_SERVICE_SENSE_VISION (1U << 9)   // 视觉
#define NB_SERVICE_ACT_GIMBAL   (1U << 16)  // 云台
#define NB_SERVICE_RELAY_NODE   (1U << 24)  // 中继
```

> **重要**：RPC 应用层的适配层目前**不**读这份宏表——它只认「服务表 ID」和
> 「名字哈希」。这份宏的价值在于：
> 直接使用 `nb_mesh` 的代码（例如自己写发现逻辑、或测试）可以用它填
> `cfg.service_mask`，并保持全网 bit 编号一致。
>
> 如果你希望 RPC 路径也用上这套固定编号，做法是：**让服务表里的 ID 等于你想用的
> bit 号**（例如 `CORE_FCS` 用 ID 0、`SENSE_SLAM` 用 ID 8），两者就自动对齐了。

规则：新增服务在这里分配 bit 后，**已废弃的 bit 不能复用**——编号一旦发到线上就
等同于 ABI。

#### 方式三：名字哈希（兜底，生产别依赖）

既没装服务表、也没在 `mesh_services.h` 分配 bit 时，发现层退化成
"把服务名哈希到 32 个 bit 之一"（`nb_mesh_service_bit(name)`）。

代价：**不同服务可能撞到同一个 bit**。撞了不会崩、不会误删邻居，但"查服务 X"
可能返回一个实际只提供 Y 的节点，调用失败（RPC 层报错）。

### 4.3 "我怎么知道对端有哪些服务"

不需要知道。客户端只关心"我要调的这个服务现在谁有"，用 bit 查表即可。
如果业务真的需要"列出全网所有服务"，那不属于发现层——用
`nb_participant_discovery_read()`（DDS 侧）或自己维护一张静态表。

### 4.4 服务表和 RPC 的关系（别混淆）

| 层 | 作用 |
| --- | --- |
| 服务位图（26 字节心跳） | 回答"**有没有**这项能力" |
| RPC 调用的 service/method 名字 | 回答"**具体调哪个方法**" |
| `nb_metadata_t` | 接口版本、鉴权等附加信息 |

位图里没有方法名，也不需要——方法名在 RPC 请求里。

## 5. 内部怎么实现（决定性能的部分）

### 5.1 小本本（邻居表）

- **8192 个哈希桶**（2 的幂，用位与取模）+ 链表解决冲突，键是 node_id；
- **每个服务位一条双向链表 + 轮转游标**：查"谁会 bit 9"直接取该链表的头，O(1)；
  同一个服务有多个节点时按游标轮转，不会永远打同一个；
- 节点内存**启动时一次性分配好**，运行期不再 malloc（不会因为长时间运行产生碎片，
  这对嵌入式很重要）；
- 表满时按"最久没说过话"淘汰一个，并打 WARN 日志，**不会静默丢掉新节点**。

### 5.2 线程

**每个节点只多 1 条线程**（跑事件循环），收发清扫都在这一条线程上：

```
这条线程：
  ├─ socket 可读事件  -> 收包、解析、更新小本本（一次最多取 64 个包，避免饿死定时器）
  ├─ 发送定时器       -> 发心跳（间隔是动态的：Fast-Join 50ms / 稳态 1s+抖动）
  └─ 清扫定时器       -> 每 200ms 剔除过期邻居
```

业务线程查表时加一把互斥量，临界区只有"一次链表操作"，**不持锁做网络 IO**。

### 5.3 同机多实例的一个坑（已修）

如果一个进程里 / 一台机器上跑多个节点，它们会共用同一个发现端口。此时：

- **必须只开 `SO_REUSEADDR`**，让每个 socket 都能收到组播的一份副本；
- **绝不能开 `SO_REUSEPORT`**——内核会把报文"负载均衡"给其中一个 socket，
  结果是每个节点只看到一部分邻居（我们实测踩过这个坑）。

## 6. 能不能顶住 1000~5000 节点

### 6.1 先算账（每个节点的开销）

| 项 | 数值 | 说明 |
| --- | --- | --- |
| 发出去的流量 | 26 B × 1/s ≈ **26 B/s** | 与节点数无关！这是关键 |
| 收进来的流量 | 26 B × (N-1)/s | N=1000 → 26 KB/s；N=5000 → 130 KB/s |
| 收包率 | (N-1) 包/秒 | N=1000 → 1000 pkt/s；N=5000 → 5000 pkt/s |
| 内存 | 约 **750 KB**（含 8192 桶表 + 邻居池） | 实测单进程常驻 |
| 查表开销 | **0.44~0.46 μs/次** | 实测，N=1000 与 N=5000 一样 |

再换算成"整个网络"：组播的好处是**一个包全网只发一次**，交换机负责复制。所以：

- N=1000：每秒 1000 个 26 字节的包 = 26 KB/s 的组播流量（全网），
  落到每个节点是 1000 pkt/s；
- N=5000：每秒 5000 个包 = 130 KB/s（全网），每节点 5000 pkt/s。

**结论：带宽完全不是瓶颈，1000 节点只占百兆网的万分之几。**

### 6.2 真正的瓶颈在哪

1. **每秒收包次数**（5000 节点 = 每节点每秒 5000 个包）。这需要 CPU 能及时
   处理完；我们的解析是"查表 + 拷 26 字节"，单核轻松吃到几十万 pkt/s。
2. **交换机的组播复制能力**：千兆交换机给 1000 个端口各复制一份 26 字节包，
   压力很小；但如果网络里用的是低端交换机/无线，要看它的组播表容量。
3. **上电瞬间的尖峰**：所以才有 Fast-Join 只发 3 次 + 稳态抖动。

### 6.3 实测结果（不是估算）

在 8 核机器上跑**真实进程**（每个都是一个完整节点）：

| 节点数 | 预期每个看到 | 实测 |
| --- | --- | --- |
| 8 / 16 / 32 / 64 | N-1 | 全部精确 |
| 200 | 199 | 200/200 都看到 199 |
| 500 | 499 | 500/500 都看到 499 |
| **1000** | **999** | **1000/1000 都看到 999** |

**1000 节点集群里零预知调用**（998 个纯成员 + 1 个只提供服务 EchoService 的节点 +
1 个什么都不配置的客户端）：

```
→ CALL_OK=1 status=0 len=17
```

接收侧压力测试（注入 1000 / 5000 个不同节点的心跳）：

| 注入数 | 全部入库耗时 | 寻址时延 |
| --- | --- | --- |
| 1000 | 72 ms | 0.435 μs |
| 5000 | 282 ms | 0.460 μs |

### 6.4 所以，1000~5000 到底行不行

**行**，并且有余量，但要注意三条前提：

1. **5000 个节点不要挤在一台机器上**。单机 1000 进程时 8 核负载已经到 141
   （虽然结果仍然正确）；真实部署是每台机器 1 个节点，每条机器每秒只处理
   (N-1) 个 26 字节包，压力小两个数量级。
2. **服务种类 ≤ 32**。超过 32 个服务，位图就装不下，需要扩成 64 位（报文加 4 字节，
   协议小改版）或者改用"按需拉服务列表"（会引入握手）。
3. **一个编队一个组播组**。5000 个节点建议按任务拆成几个编队（每个编队 ≤ 1000），
   网络层面也更干净。

### 6.5 什么时候会撑不住

- 节点数上万，且都在同一个组播组：每节点每秒上万包，接收侧会吃力；
  这时应该分层（分组 + 组间聚合）或换成本地化的服务路由。
- 节点频繁上电掉电（每秒几十个变动）：每次变动都是全网一次 JOIN/LEAVE，
  抖动机制能缓解但不能消除。
- 无线网络：组播在 WiFi 上非常不可靠（会降速到最低速率），
  无人机集群如果走无线，建议改成"组播发现 + 单播保活"或直接单播目标列表。

## 7. 配置项

RPC 配置里的 `rpc.discovery` 块：

| 字段 | 默认 | 含义 |
| --- | --- | --- |
| `group` | 由 `formation` 推导 | 组播地址；`""` 表示只用单播目标 |
| `port` | 41953 | 发现端口 |
| `formation` | 0 | 编队号（隔离用） |
| `service_mask` | 0 | 本节点提供的能力位图（一般由代码按注册的服务自动算） |
| `heartbeat_interval` | 1000 ms | 心跳周期 |
| `lease` | 1500 ms | 多久没心跳就认为下线 |
| `peers` | 空 | 定向单播目标（组播不可用时用） |

```json
{
  "rpc": {
    "mode": "mesh",
    "discovery": {
      "formation": 7,
      "heartbeat_interval": "1s",
      "lease": "1500ms"
    }
  }
}
```

## 8. 失败的时候会怎样

| 情况 | 表现 |
| --- | --- |
| 丢一个心跳 | 没事，租约是心跳的 1.5 倍 |
| 节点掉电 | 最多 1.5 秒后从全网消失，之后调用立刻 NOTFOUND |
| 节点正常退出 | 立刻消失（发 LEAVE） |
| 同一 node_id 重启换了 IP | 新心跳直接覆盖，不会有两个记录 |
| 表满了 | 淘汰最久没说话的，发 WARN |
| 对端只通告能力但没开 RPC 端口 | 视为不可调用，寻址返回 NOTFOUND |
| 组播被禁用 | 配 `peers` 走单播，功能不变 |

## 9. 自己验证一遍（不用改代码）

仓库自带一个诊断工具 `tools/mesh_probe`：

```bash
# 1) 两个进程：一个提供 EchoService，一个什么都不知道去调
./mesh_probe serve 42 239.255.42.1 45001 &
./mesh_probe call  42 239.255.42.1 45001      # 期望 CALL_OK=1

# 2) 1000 个进程互相发现（判据看运行中的 T 行，别看 EXIT 行）
for i in $(seq 0 999); do
  ./mesh_probe mutual 13 239.255.13.1 47200 15 $i 0 &
done
# 每个进程应打印 peers=999

# 3) 接收侧容量：注入 5000 个邻居
./mesh_probe scale 77 239.255.77.1 45100 5000
```

## 10. 已知限制（别当它没有）

1. **32 个服务上限**（位图宽度）。要更多就得扩报文或换方案。
2. **没有序号**：极端乱序时 1.5 秒窗口内可能短暂指向旧地址，下一次心跳纠正。
3. **组播是单向广播**：没有"我问你答"，所以节点之间不能协商，只能各自维护本地视图。
4. **靠名字哈希兜底时可能碰撞**：生产环境请用固定 bit 或服务表。
5. **IPv4 only**：报文里 `real_ip` 是 4 字节，没给 IPv6 留位置。
6. **一个节点一个 RPC 端口**：想给不同服务分端口，当前方案不支持。
