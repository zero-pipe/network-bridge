# RTPS 讲透：跟着 A 发温度、B 收温度，一路看懂 RTPS

> **RTPS** 指 OMG DDS 的线缆协议 *Real-Time Publish-Subscribe*（实时发布订阅），不是流媒体的 RTSP。
>
> 这份文档的讲法和你平时看的参考手册不一样：它**不讲知识点目录**，而是跟着一条具体的主线走——
> A 机器发"温度"，B 机器收"温度"，后来 C 也加进来——**每讲一个机制，都先讲情景，再看网线上的
> 报文格式，再画交互时序，最后给你一个能对照的小案例**。TCP/UDP/组播/字节序这些你已经很熟，本文不解释。
>
> 看完你应该能做到：对着 Wireshark 抓的包，说出每一段在干什么；看到"连上了却收不到数据"，知道去查哪一层；
> 看到大报文慢，知道瓶颈在哪。报文/时序的速查表在文末，API 对象模型见 [`rtps-api.md`](rtps-api.md)。

## 全书主线（先认识一下演员）

```text
  A 机器                                         B 机器
┌──────────────┐       局域网/网络        ┌──────────────┐
│  A 程序       │  ───────────────────▶  │  B 程序       │
│  发布 "温度"   │   23.5℃、24.1℃、…      │  订阅 "温度"   │
└──────────────┘                          └──────────────┘
        （之后 C 机器也会加入，也要订阅温度）
```

A 只管"我把温度发出去"，B 只管"我要温度"，**谁也不用知道对方的存在、IP、有几个**。
下面每一章，都是围绕这条主线，把"这件事怎么在网线上做到"一层层拆开。

## 第一部分：先把道理讲明白（不碰字节）

### 第 1 课：它到底要解决什么问题

最笨的做法是：A 记住 B 的 IP，主动连过去发。但这样 A 就得知道"谁要"，B 晚启动还得处理重连，
来一个 C 就得改 A 的代码——**发的人和收的人被死死绑在一起了**。

RTPS 要做的就一句话：

> **A 只管"我把温度发出去"，B 只管"我要温度"，中间由协议自动把他们对上。**
> 就像收音机：电台只管广播，不知道也不关心谁在听；听众只管调到那个频率，谁都能听。

后面所有"发现、QoS、心跳、补包、切包"，都只是为了把这件事在**会丢包的网络上、自动地、可靠地**做成。

**一句话总结**：让发和收互相解耦，中间的撮合交给协议。

### 第 2 课：A 和 B 靠什么"对上号"

两台机器怎么找到彼此？大家会**自动加入一个公共的"大群聊"**（就是组播，你懂，跳过原理）。
流程三步：

1. **自我介绍。** A 启动，往群里喊："我是 A，我**发布**一个叫 `温度` 的数据。"
   B 启动，喊："我是 B，我**订阅**一个叫 `温度` 的数据。"（这个"名字"叫 **topic 名**，当成一个标签。）
2. **各记小本本。** 每台机器都听群，谁喊了什么都记下来——我手上有哪些发布者、哪些订阅者。
3. **本地配对。** A 翻小本本：B 要 `温度`，我正好发 `温度` → 配对，之后直接私聊发数据，不再在群里喊。

**关键**：配对是**各自在家算出来的**，不需要中心服务器，所以没有单点、谁加进来都自动生效。

**一句话总结**：公共频道里互相"自我介绍 + 报标签"，各自建小本本，本地按标签配对，配上了就私聊。

### 第 3 课：光名字一样不够——"质量要求"也要对得上

A 喊"我发温度"、B 喊"我要温度"，名字一样。但若直接配对可能出事：

- A 是**尽力而为**：发出去丢了就丢，不负责补。
- B 却要求：**一条都不能少，丢了必须补**。

硬凑一起，B 会一直等补不来的数据，等于坏掉。所以**配对前双方还报一个"质量要求"，对得上才连**。
这个质量要求就是 **QoS**（服务质量），一句话描述"这条数据我要什么待遇"。常打交道的就三种：

| QoS 维度 | 取值 | 生活类比 |
| --- | --- | --- |
| **可靠性** | 可靠 / 尽力而为 | 挂号信 vs 平信 |
| **历史** | 保留全部 / 只留最新 | 看聊天记录 vs 看温度计当前度数 |
| **持久性** | 后来的也能拿到旧的 / 只拿连上之后的 | 直播回放 vs 只看直播 |

配对规则只有一句：**A"能提供的" ≥ B"要求的"**。A 能可靠发、B 只要求尽力而为 → 能配（给多了没关系）；
A 只能尽力而为、B 要求可靠 → **配不上，静默不连**。

> 💡 排障铁律：**"发现得到、topic 名一样、就是不收数据"——十有八九是 QoS 对不上**。
> 因为配不上是**静默发生**的，不报错，最容易让人抓瞎。

**一句话总结**：topic 名决定"是不是同一份数据"，QoS 决定"能不能连"；能提供 ≥ 要求才配对。

## 第二部分：网线上到底长什么样

### 第 4 课：一个 UDP 包里装的是什么

一句话：**一个 RTPS 数据包 = 一个小信封头 + 一串"带标签的小盒子"。**

比喻成快递：**纸箱（= 整个 UDP 包）**，箱上贴**快递单（= 信封头）**写明从谁来到谁去；箱里塞了好几个
**小盒子（submessage）**，每个盒子贴标签："这是心跳""这是数据""这是在说缺哪些"。

```text
┌─────────────────────────────────────────┐
│  信封头（20 字节，固定）                     │  ← "这是 RTPS 包，我是参与者 X"
├─────────────────────────────────────────┤
│  盒子① [标签=数据]     内容…                 │  ← 一条数据
│  盒子② [标签=心跳]     内容…                 │  ← "我有 1~10 号"
│  盒子③ [标签=ACKNACK]  内容…                 │  ← "我缺 4 和 7"
└─────────────────────────────────────────┘
```

**为什么一包里塞好几个盒子？** 这就是快的原因：**一次寄一个箱子（一次系统调用），里面塞 10 条数据，
比寄 10 次快得多**。RTPS 的高吞吐，根子之一就在这（后面第 12 课还会展开）。

### 信封头那 20 字节

```text
偏移  长度  内容            你可以理解为
0     4     "RTPS"         箱子的商标——抓包一眼认出
4     2     版本号          协议版本
6     2     厂商标识        谁家实现（Cyclone? 本栈? …）
8     12    参与者代号       寄件人是谁（12 字节，给这台机器/进程起的名）
```

### 每个盒子的头（4 字节）

```text
第1字节  标签        ← 这是什么盒子（数据？心跳？ACKNACK？…）
第2字节  旗子        ← 一组开关（下一课专讲字节序）
第3-4字节 长度        ← 这个盒子内容多长，好让我知道下一个盒子从哪开始
```

那个**"长度"极关键**：解析的人不用认识每一种盒子——遇到不认识的标签，靠长度**直接跳过**，继续读下一个。
所以协议以后加新盒子类型，老程序也不会崩。

**一句话总结**：包 = 20 字节信封头（`RTPS` 开头 + 12 字节参与者代号）+ 一串小盒子；每盒 4 字节头（标签 + 旗子 + 长度）。

### ★ 怎么判断"一包读完了 / 一个盒子读完了"

这是你问的"怎么判断完整的一包"，先把"拆包"这层讲清：

1. **一个 UDP 数据报 = 一个完整"包"**。`recvfrom` 的返回值就是这包的总长度——UDP 保证边界，你收一次就是一整包，
   不会半包。（这点你本来就懂，只是别忘了它是 RTPS"拆盒子"的起点。）
2. **盒子怎么一个个拆？** 从信封头后面开始，**读一个盒子头，得到"长度"，跳到下一个盒子头**，如此往复。
3. **什么时候到头？** 两种结束信号：
   - 读到的"长度"字段**是 0** → 表示"这是最后一个盒子，一直延伸到包末尾"（别再往后跳）；
   - 或者**已经走完整包的长度** → 结束。
4. **注意对齐**：每个盒子按 **4 字节对齐**，盒子之间可能垫 0~3 个填充字节。跳下一个盒子时，要按 4 字节对齐位置走。

**一句话总结**：一包=UDP 一次收的全部字节；盒子里靠"长度"字段串起来往后走；长度字段为 0 或走到包尾就停；盒子按 4 字节对齐。

### 第 5 课：那个"旗子"字节——新手头号坑（字节序）

第 2 字节 **flags** 是一组开关，**最要命的是最低位 bit0**：

> **bit0 = 这个盒子里的数字，是大端还是小端写的。0 = 大端，1 = 小端。**

也就是说——**字节序不是全局统一的，而是"每个盒子各自声明"**。同一个包里，盒子①可能小端、盒子②可能大端，都合法。

正确读法：**每读到一个盒子，先看它第 2 字节的 bit0，决定这个盒子的内容（包括它自己的"长度"）按大端还是小端解释**，再读下一个。

**踩坑现场**：很多人想当然"整条消息我按小端读"，结果碰上一个厂商发了大端的盒子，里面的"长度"读出个天文数字，
直接越界、解析全乱。不是你笨，是协议就这么设计的——**它允许混着来，你必须逐盒看旗子。**

这个 flags 其它几位**随盒子类型变**：比如"数据"盒子某一位表示"这是正常数据还是删除通知"；"心跳"盒子某一位
表示"这是最后一条、别回了"。**旗子要和盒子标签配着看。**

**一句话总结**：flags 的 bit0 决定"这个盒子按大端还是小端读"，每个盒子可以不同——必须逐盒看，不能全局假设。

### 第 6 课：字节序这坑，一次讲干净（两个独立声明点）

精确讲，真正**各自独立声明字节序的地方有两个**：

**① 盒子旗子**（上节课那个 bit0）——管这个盒子**自己的数字**（长度、里面的序号、ID），按大端还是小端读。

**② 数据的封装头**——管**真正业务数据**（温度值那些）的字节序。注意业务数据是**另外包一层**才塞进"数据盒子"的，
这一层开头有 **4 字节封装头**，头两个字节就是代号，直接告诉你"接下来数据是大端还是小端"：

```text
封装头前 2 字节（代号）   含义
   00 00                 CDR，大端
   00 01                 CDR，小端
   00 03 / 00 07 …       其它变体（先不用记）
```

**③（不算独立）数据里的字段**——封装头把字节序定死了，后面所有字段都跟着它走，不会每个字段再单独声明。序号那些
盒子内部数字也一样，跟着①的旗子走。

**关键结论：①和②可以不一样。** 一个"数据盒子"，盒子自己的数字可能标着大端（旗子 bit0=0），但它装的业务数据封装头
写着 `00 01`（小端）。**读盒子框架看①，读业务数据看②，各用各的。**

**为什么这么拧巴？** 两层是不同的人负责：外面那层（盒子）是 RTPS 传输框架，要读序号/长度；里面那层（业务数据）是
DDS 应用的序列化格式（CDR），自成一家。各带各的字节序声明，互不依赖。

**一句话总结**：两个独立的字节序声明点——盒子旗子（管框架）、数据封装头（管业务数据），两者可不同；层内字段跟着本层走。

## 第三部分：一条数据（Change）内部拆解

### 第 7 课：数据带"序号"——可靠补包的骨架

还记得第 4 课"读者点名补货"要能说"我缺 4 号和 7 号"吗？凭什么能点名？因为**每条数据都带一个序号**。
A 从 1 开始，每写一条 +1。

**坑在这里（一定要念一遍）：序号是 64 位，但拆成两段存，高 32 位是"有符号"的，低 32 位是"无符号"的。**

```text
序号（8 字节）=  高 32 位(int32，有符号) + 低 32 位(uint32，无符号)
```

- 最小合法序号是 **1**；**0 表示"未设置"**；
- 有一个特殊值 `高=0x7fffffff, 低=0xffffffff` 表示"**永不确认**"（哨兵）。

**为什么高半有符号是个坑？** 如果你图省事把它当普通 `uint64_t` 读，单条写入累计超过约 21 亿条时，序号会"跳负"，
可靠层直接错乱。21 亿听着远，benchmark 跑几小时就摸到了。**永远按（高, 低）两段分别读。**

> 不同写者的序号**各算各的**，互不相干——A 的 5 号和别的发布者的 5 号没有关系。

**一句话总结**：每条数据带 64 位序号（高半有符号 + 低半无符号），≥1，0=未设置，有个"永不确认"哨兵；别当 uint64 硬读。

### 第 8 课："数据盒子"里面到底怎么排

`DATA` 盒子（标签 `0x15`）是装数据的主力。它的体，从前到后：

```text
extraFlags(2) | octetsToInlineQos(2) | readerId(4) | writerId(4) | writerSN(8)
───────────────────────────── 以上是"标准框架头" ─────────────────────────────
| [可选的内联小纸条：key 哈希 / 状态位]     ← 比如"删除某实例"
| 真正的业务数据（带第 6 课那个 4 字节封装头）
```

两个字段要懂：

- **`octetsToInlineQos`**：告诉你"标准框架头有多长，业务数据从哪开始"。别硬编码数字，按它算。
- **业务数据结束在哪？** 盒子的"长度"(第 4 课那个)给了整盒长度，减去内联小纸条部分，剩下就是业务数据 + **最多 3 字节对齐填充**。
  **所以解码时必须容忍尾部 1~3 个填充字节**——有的实现不看填充长度，就会"最后一个字段读越界"。

> **这条也回答了"怎么判断一个数据盒子读完整"**：靠盒子的"长度"字段划定边界，尾部多余 0~3 字节是对齐填充，丢弃即可。

**一句话总结**：数据盒子 = 标准框架头（含 `octetsToInlineQos` 指出业务数据起点）+ 可选内联纸条 + 业务数据；末尾最多 3 字节填充要忽略。

### 第 9 课：key / 实例 / "删除通知"

想象温度不是一条，而是"很多温度计的读数"，每支温度计有编号。这就引出 **key**：

- **无 key 的 topic**：整个 topic 算一个"实例"。
- **有 key 的 topic**（某些字段被标 `@key`，比如温度计编号）：**同一个 key 值 = 同一个实例**。实例的身份用一个
  **16 字节的哈希值（instance handle）** 指代。
- **删除通知（dispose）**：A 要表达"3 号温度计下线了"，不需要发温度值，只发这个实例的"删除通知"——里面只带 key/哈希，
  业务数据可以为空。这在数据盒子里就是靠"内联小纸条 + 状态位"表达的。

**一句话总结**：key 决定"这条数据属于哪一条"，keyed topic 用 16 字节哈希当实例身份；删除某条时只发 key + 状态，不带数据。

## 第四部分：发现——A 和 B 具体怎么"自我介绍、对上号"

第 2 课说了"公共频道里互相报名字"，这章把它落到具体报文和时序。这是最容易懵、也最核心的一段，**一定要分清两个阶段**。

### 第 10 课：端口为什么能"撞上"（先解决能不能找到人）

A 和 B 在同一个"群聊"里，可这个群聊的具体地址（组播 IP + 端口）是怎么算的？**按公式算，双方算出同一组就撞上了。**

```text
基础端口 = 7400 + 250 × domainId + (偏移) + 2 × participantId
  偏移： 0 = 内置多播(SPDP)   1 = 内置单播   10 = 用户多播   11 = 用户单播
group = 239.255.0.1（默认的发现组播地址）
```

举例（domainId=0、participantId=0）：

```text
SPDP 多播端口 = 7400 + 0 + 0 + 0 = 7400    →  发到 239.255.0.1:7400
```

> 💡 **"同网段却互相看不到"的头号原因**：两端 **domainId 不一样**。domainId 不同，端口完全不同（差 250 的整数倍），
> 永远撞不上。同机两进程还要 **participantId 不同**，否则抢同一组端口。

**一句话总结**：端口 = `7400 + 250×domainId + 偏移 + 2×participantId`；同域才能撞上，domainId 不同=永远发现不了。

### 第 11 课：两个阶段——SPDP 认人，SEDP 交换明细

```text
阶段一 SPDP（Participant Discovery）：   "网络上有哪些参与者？"
   多播 + 周期喊话，不可靠，靠"租约"判活。
        │  发现某个参与者后，拿到它的代号 + 内置端点地址
        ▼
阶段二 SEDP（Endpoint Discovery）：       "它有哪些 writer/reader，QoS 如何？"
   从 SPDP 拿到的地址【单播】、【可靠】地交换"端点名片"
        │  拿到名片后，本地做 topic/QoS/类型匹配
        ▼
   匹配成功的 writer↔reader 开始发业务数据
```

### 阶段一：SPDP——参与者互相喊话（认人）

- A 启动，每隔一会儿往群聊（`239.255.0.1:7400`）发一条"我在"的自我介绍：**我是谁（参与者代号）、我收发的地址、
  我的租约多长**。
- **它是不可靠的**：发几次，丢了无所谓，下一轮再喊。
- **怎么判断对端"死了"？** 靠**租约（lease）**：一段时间没再收到某参与者的"我在"，就认为它失联，回收它的所有端点，
  并通知上层"这些发布者没了"。**没有 TCP 连接，靠租约判活**——这是从"数据中心"推导出来的设计。

时序（A 和 B 互相认人）：

```text
A ──"我在(A)"──▶ 239.255.0.1:7400
B ──"我在(B)"──▶ 239.255.0.1:7400
                （双方都从群聊听到对方 → 各自小本本记下：发现了 B / 发现了 A）
……（周期重复，一直喊，直到一方消失一段时间=租约过期）……
```

### 阶段二：SEDP——交换"端点名片"（对号）

认到人之后，A 和 B **私聊（单播）**、而且**用可靠方式**，交换各自端点的名片。为什么这里要可靠？因为**名片丢了就匹配不上，必须补**——所以你会在这看到心跳/补包（第五部分那套）。

名片 = 一大串"配置项"（topic 名、类型名、端点代号、可靠性、持久性、分组名……）。**你上节课理解的 QoS，全在这张名片里。**

时序（A 发布温度、B 订阅温度，直到配对）：

```text
A ──(单播·可靠) 名片: 我是"发布", topic=温度, 可靠, …──▶ B
B ──(单播·可靠) 名片: 我是"订阅", topic=温度, 可靠, …──▶ A
        │
        ▼
   A 本地翻名片：B 要 温度、QoS 我能满足 → 配对成功！
   B 本地翻名片：A 发 温度、QoS 我接受     → 配对成功！
        │
        ▼
   （此后 A 直接用 DATA 把温度发给 B）
```

> 💡 **"发现"和"数据"是两码事**：你抓包看到一堆 `writerId/readerId` 是"内置"的 DATA（名片），那不是你的业务数据。
> 业务数据的 writer/reader 才是你自己的端点。看内不内置就能区分。

**一句话总结**：SPDP 用多播不可靠地"认人"（靠租约判活），SEDP 用单播可靠地"交换名片"（QoS 都在这），拿到名片后本地按 topic/QoS 匹配。

## 第五部分：可靠传输——UDP 会丢，怎么补（时序详解）

### 第 12 课：心跳 → 点名 → 补货（三段式）

第 3 课知道了"可靠=读者点名补货"。这章画出确切时序。假设 A 要发 1~10 号，UDP 丢了 4、7：

```text
① A → B   HEARTBEAT: "我手头有 1~10 号"          （我有什么）
② B → A   ACKNACK : "我确认到 3 号；4、7 我缺"      （我缺什么）
③ A → B   重发 4 号、7 号（从历史本里翻出来）        （补货）
④ B 收齐，可能再回一个"都收到了"…
```

两个盒子的内部关键点：

- **心跳盒子（HEARTBEAT）**：带"第一个序号、最后一个序号"（firstSN, lastSN），意思是"从我这儿起，这段我都有"。
- **ACKNACK 盒子**：带一个"基准序号 + 一张位图"。**位图里"置位=缺（要重传），清零=已收到"**；基准之前的序号都视为已确认。
  它还能带个"最后一条"标记（FINAL），表示"这是我最后一句，别再回我了"，用来收敛来回。

对比 TCP：TCP 是发送方推窗口、逐包确认；RTPS 是**发送方定期报家底、接收方点缺货、发送方补货**。**一个是推，一个是点名要。**

**一句话总结**：写者报进度（心跳：我有 1~10）→ 读者点名缺哪些（ACKNACK：缺 4、7）→ 写者从历史本补发。可靠=读者驱动。

### 第 13 课：历史本满了怎么办——GAP 解死锁

A 的历史本有大小上限（内存有限），比如只留最近 5 条。数据太快时，4 号这种老的**已被挤掉、永远拿不出来**。
那 B 还在喊"补 4 号"，A 补不了，B 就永远卡在 4 号前——死锁。

RTPS 用 **GAP** 解决：

> A 告诉 B："**这段（1~4 号）你就当收到了，我不会再发。**"（没内容，但别等。）
> B 收到就把进度跳过去，不再纠结 4 号。

**一个反直觉但极重要的结论：**

> **"可靠" ≠ "一条都不丢"。** 如果 A 是"可靠 + 只留最新 5 条"，而 B 处理太慢、跟不上，老数据就会被挤掉、被 GAP 跳过。
> B 最终拿到的是**较新的快照**，中间那几条**真没了**，但系统没坏——这是设计如此。

真想一条不丢，得配"**历史保留全部（KEEP_ALL）**"+ 足够资源。所以选 QoS 前先问自己：

- 要**最新状态**（温度、行情）→ 只留最新，丢了就丢了，下条马上来；
- 要**每条都不能少**（日志、事件）→ 保留全部。

> 💡 "我明明开了可靠，怎么还是丢了中间几条？"→ 查历史是不是"只留最新"。

**一句话总结**：GAP=写者声明"这段永不再发、别等了"，打破补不回来的死锁；可靠不等于不丢，取决于历史留多少。

## 第六部分：切包与拼包——大样本怎么过 MTU

### 第 14 课：怎么切（写者端）

一条温度很小，一个盒子装得下。但如果 A 发的是一张 200KB 的图片，一个 UDP 包放不下（MTU 限制），怎么办？
**切成多片，每片单独发。**

> 注意别和"聚合"搞混：
>
> - **聚合** = 很多**小**数据塞进一个包（第 4 课，为了省系统调用）；
> - **切包（分片）** = 一个**大**数据切成多个包（本节，一个大样本装不下）。
> 一个是"小合大"，一个是"大拆小"，方向相反。

大样本超过单包预算时，写者用 **DATA_FRAG 盒子**（标签 `0x16`）切片。每个分片的关键字段：

```text
sampleSize           整个样本一共多少字节（好让接收端知道要拼到多大）
fragmentStartingNum  这一片是从第几个字节开始的
fragmentsInSubmessage 这一盒里装了几片
fragmentSize         每片的字节数
… +  这一片的数据
```

**切多大？由写者按传输 MTU 决定**（不是双方协商的硬值；本仓库取 1028 字节一片，见 `rtps-timing.md`）。
通常是"一片一个 UDP 包"发出去。

**一句话总结**：大样本超单包 → 写者按 fragmentSize 切成若干 DATA_FRAG，每片自带"总长/起始位置/片大小"，一片一般一个包。

### 第 15 课：怎么拼（接收端）+ 怎么判断"一个样本收完整了"

这就是你问的第二个"怎么判断完整"。接收端收到各分片，靠 `fragmentStartingNum` 把它们拼回原样本。

**判断"一个样本是否完整"的规则：**

> 把收到的分片，按"起始位置 + 这一片长度"，覆盖住整段 `[0, sampleSize)` → 就拼完整了。

举例：A 发一个 sampleSize=3000 的样本，fragmentSize=1028 → 切成 3 片（0~1027、1028~2055、2056~2999）。

```text
分片A(0..1027)  分片B(1028..2055)  分片C(2056..2999)
   收到 ✓          收到 ✗(丢了)         收到 ✓
→ 缺口 [1028,2055)，样本不完整
→ 接收端发 NACK_FRAG："我要从 1028 起的那一片"
→ A 补发分片 B
→ 三片凑齐覆盖 [0,3000) → 一个完整样本拼好，交给上层
```

两个要点：

- **分片缺了没人催 → 卡住**。所以可靠模式下，接收端会像"点名要数据"那样，用 **NACK_FRAG 点名要某个分片**；
  还有重组超时机制，长时间拼不齐就放弃。
- **拼包是传输层的事，对应用透明**：应用只管"我发了一个 200KB 的样本"和"我收到一个 200KB 的样本"，中间的切和拼它看不到。
  但它对**吞吐/延迟**影响巨大（见第 17 课）。

**一句话总结**：接收端按"起始位置+长度"把分片拼回原样本；分片覆盖满 `[0, sampleSize)` 才算完整；缺片用 NACK_FRAG 点名要，重组超时会放弃。

## 第七部分：把整条主线走一遍

### 第 16 课：端到端——A 发温度到 B 收温度，全过程时序

把前面所有零件串起来，看一遍完整生命线：

```text
【1. 认人】SPDP（多播·不可靠）
A ──"我在(A)"──▶ 239.255.0.1:7400      B ──"我在(B)"──▶ 239.255.0.1:7400
     （彼此从小本本记下：发现了对方）

【2. 换名片】SEDP（单播·可靠）
A ⇄ B   名片: topic=温度，我发布 / 我订阅，可靠，…        ← 这里会走心跳/ACKNACK
     （各自本地匹配：topic 对、QoS 兼容 → 配对成功）

【3. 发数据】DATA（单播）
A ──DATA 1号 23.5℃──▶ B
A ──DATA 2号 24.1℃──▶ B
A ──DATA 3号 23.9℃──▶ B   （错了，假设 4 号丢了）

【4. 补包】HEARTBEAT / ACKNACK / 重发
A ──HEARTBEAT 我有1~4──▶ B
B ──ACKNACK 我缺4号──▶ A
A ──重发 DATA 4号──▶ B
     （B 收齐）

【5. 大样本（如果发的是图片）】DATA_FRAG / NACK_FRAG
A ──DATA_FRAG 0..1027──▶ B
A ──DATA_FRAG 1028..2055──▶ B
A ──DATA_FRAG 2056..2999──▶ B
     （若丢一片，B 用 NACK_FRAG 点名要；凑齐 [0,3000) 拼好）

【6. 删除一条】DATA（带 key + 状态位）
A ──DATA 带 key(3号温度计)+dispose──▶ B
     （B 得知 3 号实例已下线，状态变 NOT_ALIVE_DISPOSED）

【7. 有人走了】SPDP 租约过期
   一段时间收不到 A 的"我在" → B 判定 A 失联 → 回收端点，通知"发布者没了"
```

### 第 17 课：性能——为什么有的快有的慢

你已经懂底层网络，这里只讲 RTPS **特有**的杠杆，都能从"数据中心 + UDP + 可靠"推出来：

1. **聚合装盒**（第 4 课）：一个包装多条数据，摊薄头部和系统调用。**吞吐第一杠杆是"每包装几条"**。
2. **系统调用批处理**：一次 `sendmmsg`/`recvmmsg` 刷多包，比循环 `sendto` 省海量 syscall。
3. **零拷贝 / 拼接发送**：报文的头由引擎生成，业务数据直接引用、不搬家（scatter-gather 一次发出）；可靠模式只保留一份历史拷贝供重传。
4. **历史槽位复用**：可靠历史是环形槽，槽位缓冲复用而非每次 malloc/free。**可靠路径的 malloc 是隐形杀手**（本仓库靠它把可靠吞吐翻了几倍）。
5. **MTU 自适应**：单包上限不是常数，loopback/大 MTU 链路放宽容纳更大的单报文。
6. **可靠的成本**：多出"保留历史（一次拷贝）+ 心跳/确认往返"。小包高频时摊不薄，是结构性开销；大包时聚合收益盖过它。
7. **大消息的串行陷阱**：一条大样本切 N 片，如果"在途分片数"受限，会逐片串行发出，**延迟 ≈ N × 单窗**。
   本仓库实测：64KB 单流仅 93 QPS，把"每轮在途分片数"在回环上放开后跃到 293（3.2×）；而**改分片大小几乎没用**——
   **遇到大报文慢，先看在途量，别急着调 MTU。**

**一句话总结**：聚合、批 syscall、零拷贝、槽位复用、MTU 自适应是提速杠杆；可靠有结构性成本；大报文慢先查在途分片并发量。

## 第八部分：排障与速查

### 第 18 课：从"看不到人"到"数据丢了"的排查树

```text
Q1. 两端互相发现了吗？
    看同 domain 多播 239.255.0.1 上有没有对方 SPDP。
    ├─ 没有 → domainId 不同 / 端口算错 / 多播被禁 / 防火墙 / 同机 participantId 冲突
    │          / 没配 initial peers。          → 查第 10 课端口公式、多播开关。
    └─ 有   → Q2
Q2. 端点匹配了吗？
    看 SEDP 名片里的 topic 名 / 类型名 / QoS / 分组名。
    ├─ 不匹配 → topic 名不符 / type 名不符 / QoS 不兼容 / 分组名不重叠。→ 逐个比对名片（第 3、11 课）。
    └─ 匹配   → Q3
Q3. 匹配了，为什么没数据？
    ├─ 写者根本在写 / 被资源上限卡住
    ├─ 读者后启动而写者是"只发连上之后的"（VOLATILE，无补发）→ 改持久性
    ├─ 被 reader 的内容过滤 / 时间过滤挡掉
    └─ 数据到了但你处理太慢被"只留最新"挤掉 → 改"保留全部"或加深历史
Q4. 数据时有时无？
    ├─ 尽力而为：丢了正常，要可靠就上"可靠"
    ├─ 可靠仍丢：历史太小被 GAP 跳过 / 心跳周期太长 / 读者背压 / 分片重组超时
    └─ 跨机：UDP 丢包 / MTU 黑洞（大包被中间设备丢）→ 降单包大小
```

**Wireshark 速记**：过滤 `rtps`；看 `writerEntityId/readerEntityId` 是不是"内置"来区分名片 vs 业务数据；
看 HEARTBEAT 的 `[first,last]` 和 ACKNACK 的 `base + 位图` 还原补包；看名片里的参数直接读对端 QoS。

## 速查表

**信封头**：`"RTPS"` + 版本(2) + 厂商(2) + 参与者代号(12) = 20 字节。
**盒子头**：标签(1) + 旗子(1) + 长度(2)；旗子 bit0：0=大端 / 1=小端；长度=0 表示延伸到最后；4 字节对齐。

**常用盒子标签**：数据 `0x15` / 分片 `0x16` / 心跳 `0x07` / ACKNACK `0x06` / GAP `0x08` / NACK_FRAG `0x12` /
时间戳 `0x09` / 目标 `0x0e` / 来源 `0x0c`。

**序号**：`{int32 高; uint32 低}`，≥1，0=未设置，`7fffffff/ffffffff`=永不确认；高半有符号。
**封装代号**：CDR_LE `0001` / PL_CDR_LE `0003` / XCDR2_LE `0007`。
**ACKNACK 位图**：置位=缺（要重传）。

**端口**：`7400 + 250×domainId + 偏移 + 2×participantId`（偏移 0/1/10/11）；发现组播 `239.255.0.1`。

**三句话带走**：

1. 发布者不关心谁听、订阅者不关心谁发，靠 topic+QoS 撮合。
2. 底下 UDP，可靠靠"心跳报进度 → 读者点名缺 → 写者补"，GAP 解死锁。
3. 一个包=信封头+一串小盒子；大样本切成 DATA_FRAG，凑满 `[0,sampleSize)` 才算完整。
