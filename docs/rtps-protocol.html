0. 这份文档怎么读

RTPS（Real-Time Publish-Subscribe）说白了就是一套“在 UDP 上互相喊话”的二进制约定： 谁在线、我有哪些数据、你感不感兴趣、丢了怎么补。它本身不规定你发什么业务数据， 只规定怎么找到对方、怎么描述自己、怎么把字节送过去。

这份文档讲的是本仓库这套实现（src/rtps/），不是 OMG 规范的逐条翻译。 好处是：每个字段宽度、每个定时器、每条“不匹配”的判定，都能在代码里找到出处； 代价是：它只覆盖本实现真正用到的子集。

阅读约定 文中所有多字节整数默认小端（低字节在前）。十六进制写作 0x0015 这种形式。 “线上”指实际发出的字节；“解析”指收到报文后的处理。发现流程里的“名片”是 ParameterList（参数列表）的口语说法。

建议的阅读顺序：

  1. 先看第 1 章建立整体图景，别急着背字段。
  2. 要写解析器 / 抓包对照，看第 3、4 章。
  3. 要排查“为什么发现不到对方”，看第 5、6、12 章。
  4. 要排查“为什么发现到了却收不到数据”，看第 7、8 章。

配套文档：rtps-spec.md（本实现的规范性说明：字段、默认值、 限制、QoS 匹配规则与 Cyclone 互通矩阵）。规范细节以 rtps-spec.md 和 src/rtps/ 代码为准， 本文偏“线上到底长什么样、出问题怎么排”。

1. 五分钟建立直觉

1.1 四个角色

角色大白话在代码里
Participant进程里的一个“大喇叭”。它有自己的地址、自己的 ID，负责收发一切。nb_rtps_participant_t
Writer“我这儿有数据要发”。一个 writer 对应一个 topic。NB_RTPS_ENDPOINT_PUBLICATION
Reader“我这儿想收数据”。一个 reader 也对应一个 topic。NB_RTPS_ENDPOINT_SUBSCRIPTION
Topic + Type聊什么（话题名）+ 用什么格式聊（类型名）。两者都对上，才算同一个频道。topic_name / type_name

1.2 两阶段发现

RTPS 的发现分两步，像现实里的社交：

  1. SPDP（Simple Participant Discovery Protocol）：先喊“我在这儿”。 内容很少：我是谁、我的地址、我的租约多久、我支持哪些内置端点。相当于在广场上广播“我叫张三，住 3 号楼”。
  2. SEDP（Simple Endpoint Discovery Protocol）：认识之后交换名片。 内容变多：我有哪些 writer / reader、每个的 topic、type、QoS。相当于加微信后发详细资料。

顺序不能反：不知道对方地址，就没法单播名片；不知道对方有哪些端点，就不知道数据该发给谁。

1.4 一句话总结

记住这三句就够用了 发现 = 组播喊 SPDP（我在哪）→ 单播发 SEDP（我有什么）→ 双方按 topic/type/QoS 匹配 → 匹配上了才发数据。

2.1 EntityId 的构成

4 个字节里，前 3 个是 key（区分不同实体），最后一个字节是 kind（区分类型）。 kind 决定“这是 writer 还是 reader、是用户建的还是协议内置的”。

kind含义典型值
0x00未知 / 通配00 00 00 00
0x01participant 本身00 00 01 c1
0x03用户 writer（RTPS 语义为“带 key”；本实现不推导 key，数据不带 key）本实现创建的 publication
0x04用户 reader（无 key）本实现创建的 subscription
0xc2内置 writer（带 key）SPDP writer、SEDP writer
0xc7内置 reader（带 key）SPDP reader、SEDP reader

用户端点共用一个 key 计数器（next_entity_key），从 1 开始递增，与 writer / reader 无关： 第一个创建的端点 key = 1（例如第一个 writer 是 01 00 00 03），第二个创建的端点是 02 00 00 04，以此类推。

3. 报文格式

3.1 整体结构

一个 RTPS 报文（就是一个 UDP 数据报的载荷）永远是： 一个 20 字节消息头 + 一连串子消息。 子消息之间没有分隔符，全靠每个子消息自己的长度字段往下走。 

offset 0                                offset 20
[ "RTPS" ][2.4][vendor][guidPrefix]     [ submsg 1 ][ submsg 2 ] ... [ submsg N ]
  4B        1B   1B      12B             每个 = 4B 头 + 内容（补齐到 4B）

消息头：0-3 "RTPS" | 4 verMajor | 5 verMinor | 6-7 vendorId | 8-19 guidPrefix
子消息头：0 id | 1 flags | 2-3 octetsToNextHeader（内容长度，不含这 4 字节）

几个容易踩的点：

  • 子消息的内容补齐到 4 字节，补齐的 0 也算在长度里。
  • 长度字段是 16 位，所以单个子消息最多 65535 + 4 字节。数据大了必须分片（见第 8 章）。
  • 本实现只发小端报文，也基本只接受小端；E 标志永远置 1。
  • 一个包里可以塞多个子消息，也可以只塞一个。接收方按顺序处理。

3.2 消息头（20 字节）

偏移宽度字段本实现的取值 / 说明
0–34magicASCII "RTPS"（52 54 50 53）。不是“RTPS 缩写”，就是四个字符的定界符。
41versionMajor2
51versionMinor4
6–72vendorId01 9a（占位值，正式发布前要换成 OMG 分配的厂商号）
8–1912guidPrefix本 participant 的前缀，见下

GUID prefix 的 12 个字节这样来：

字节内容
0–1vendor id：01 9a
2–3ASCII "NB"（4e 42），标明是本实现
4–7当前毫秒时间戳的低 32 位（小端）
8–11时间戳高 32 位 XOR participant 指针（小端）

所以同一台机器上不同进程、不同时刻启动的 participant，前缀基本不会撞。 它不是随机 UUID，也不含 IP。

3.3 子消息头（4 字节）

偏移宽度字段说明
01submessageId见 3.5 的表
11flags见 3.4；同一位在不同子消息里含义不同
2–32octetsToNextHeader小端。= 本子消息 body 长度（含补齐），不含这 4 字节头

因此“下一个子消息从哪开始” = 当前偏移 + 4 + octetsToNextHeader。 遇到不认识的 id，直接按这个长度跳过即可（本实现就是这么处理 INFO_SRC / INFO_REPLY 的）。

3.4 标志位

位名字用在哪含义
0x01E（Endianness）所有子消息1 = 小端，0 = 大端。本实现恒为 1。
0x02Q（InlineQos）DATA / DATA_FRAG1 = 序列号后面跟一段 ParameterList（内联 QoS），再往后才是载荷。
0x04D（Data）DATA1 = 后面有序列化载荷。删除/只发 key 时清 0。
0x08K（Key）DATA1 = 载荷只是 key（实例句柄），不是完整样本。
0x04K（Key）DATA_FRAG1 = 这个分片序列承载的是 key-only 样本。注意不是 0x08：DATA_FRAG 的 0x08 没有定义。
0x02F（Final）ACKNACK1 = “不用回应”。本实现只在纯确认（numBits = 0）时置位；请求补发时清 0。
0x02F（Final）HEARTBEAT1 = “不需要 ACKNACK 回应”。本实现不发这一位。
0x04L（Liveliness）HEARTBEAT1 = 这个心跳同时断言 writer 还活着（manual-by-topic 用）。L 是 0x04，不是 0x02。
0x02I（Invalidate）INFO_TS1 = 时间戳无效，body 长度为 0。本实现只发有效时间戳。
别把 flags 当全局位图 0x02 在 ACKNACK 和 HEARTBEAT 里都是 Final，在 INFO_TS 里是 Invalidate； 0x04 在 HEARTBEAT 里是 Liveliness，在 DATA_FRAG 里却是 Key。 解析时必须先看 submessageId，再解释 flags。

3.5 各子消息

下表的偏移都从子消息第 1 个字节（id）算起，不是从 UDP 包开头算。

INFO_TS（0x09）—— 给后面的数据打个时间戳

偏移宽度字段说明
0–34子消息头id=0x09，flags=E（或 E|I）
4–74secondsint32，Unix 秒
8–114fractionuint32，单位 2-32 秒

本实现发每个 DATA 前都会先写一个 INFO_TS；时间来自系统时钟毫秒值： fraction = (ms % 1000) << 32 / 1000。 INFO_TS 对它后面所有子消息生效，直到下一个 INFO_TS。

INFO_DST（0x0e）—— 这包是给谁的

偏移宽度字段说明
0–34子消息头id=0x0e
4–1512guidPrefix目标 participant 的前缀；全 0 表示“谁都可以看”

单播 SEDP、用户数据、ACKNACK、HEARTBEAT 发送时都会带 INFO_DST，明确写给某个 participant； 组播 SPDP 不带（它本来就是喊给所有人听的）。 接收侧会按 INFO_DST 过滤：目标前缀不是本 participant 的 Entity Submessage 直接丢弃，全 0 前缀视为广播。TCP 连接在每条 RTPS 消息开始时重置该状态。

INFO_SRC（0x0c）/ INFO_REPLY（0x0f）

规范里用来声明“源 participant”和“回复地址”。本实现不发这两种子消息， 收到也不处理，直接按长度跳过。看到它们不用慌，跳过即可。

3.6 序列号、时间、位图

SequenceNumber：为什么是两个 32 位

规范里它是 64 位有符号数，线上拆成 high（int32）+ low（uint32）。 本实现内部统一用 uint64_t 表示，wire 上的 high/low 原样保留； writer 历史、reader 窗口和位图都能跨 2^32 边界推进。

时间与时长：秒 + 2⁻³² 秒

RTPS 的 Time_t 和 Duration_t 都是 8 字节：低 4 字节是秒，高 4 字节是 2-32 秒为单位的分数。 

// 把毫秒转成线上格式
seconds  = ms / 1000
fraction = ((ms % 1000) << 32) / 1000

// 无限时长
seconds = 0x7fffffff, fraction = 0xffffffff
本实现的一个土规矩 QoS 里的时长用“毫秒 = 0”表示策略没设置：这时干脆不写那个 PID，让对端按 DDS 默认值处理 （deadline / lifespan / lease 默认都是无限）。这跟“显式写一个无限大”不是一回事。

位图：bit 0 是最高位

ACKNACK / GAP / NACK_FRAG 的位图都遵循同一个反直觉约定： 第 0 位对应 32 位字的最高位 0x80000000，而不是最低位。 

base = 5, numBits = 3

bit index :  0        1        2
mask      : 0x80000000 0x40000000 0x20000000
sample SN :  5        6        7

bitmap = 0xA0000000  ->  bit0=1, bit1=0, bit2=1  ->  缺 SN 5 和 7，已收到 6
bitmap = 0x00000000  ->  三个都缺
bitmap = 0xE0000000  ->  三个都收到了

代码里造位图时用的是 1u << (31 - (i % 32))，解析时反过来。 写成 1 << i 是最常见的实现错误，会让抓包看起来“全丢”。

3.7 ParameterList（参数列表）

发现报文（SPDP / SEDP）的载荷不是结构体，而是一串“键值对”。 每个键值对叫一个 Parameter，靠 PID 区分“这是什么”。 

 ┌──────────┬──────────┬─────────────────────────┬─────────┐
 │ PID (u16)│ len (u16)│        value ...        │ padding │
 └──────────┴──────────┴─────────────────────────┴─────────┘
  2 字节      2 字节     len 含 padding，必为 4 的倍数

 结束标志：PID = 0x0001 (PID_SENTINEL), len = 0
  • PID 和长度都是小端。
  • 长度包含 value 后面的补齐字节，所以永远是 4 的倍数。这一点和某些早期实现不同，抓包时容易看错。
  • value 内部的 CDR 对齐从 value 的第一个字节重新算，不是从报文头算。
  • PID_PAD = 0x0000 用来占位对齐，内容忽略。
  • 遇到不认识的 PID：按长度跳过，不要报错（本实现对厂商私有 PID 就是这么处理的）。

发现的前提是“能找到”。这一章讲清楚：一个 participant 到底监听哪些地址、端口怎么算、 地址又是怎么告诉对方的。

4.2 组播的细节

  • 加入组播组后，TTL 设为 1，即不会跨路由器扩散，只在本地链路喊。
  • 组播回环打开，所以同一台机器上的多个 participant 也能互相发现。
  • 绑定 0.0.0.0 时，如果配置里没写 advertise_host，公告地址会退化成 127.0.0.1。
  • 关闭组播（multicast_group = ""）后，SPDP 端口也变成临时端口，只向显式配置的 peers 单播。
跨机器发现不到？先看 advertise_host 如果本机有多张网卡，默认公告的可能是回环地址。对端拿到 127.0.0.1 的单播地址， 自然发不到你。显式配置 advertise_host 指向真实网卡地址即可。

4.4 TCP 承载

TCP 不是 RTPS 规范强制的，但本实现支持，用于跨网段 / 穿透只允许长连接的场景。 注意它只是换了个搬运工：

  • SPDP 仍然走 UDP 组播/单播（否则没法发现对方）。
  • TCP 连接建立后，里面跑的仍然是完整的 RTPS 报文：20 字节头 + 子消息，没有额外的长度前缀。
  • 接收方靠“找下一个 RTPS 头”来重新同步字节流。
  • 每个连接有接收缓冲（128 KiB）和发送队列（512 KiB），超了会丢而不是无限吃内存。
  • 最多同时 16 条连接。

5. SPDP：先找到人

SPDP 只干三件事：告诉大家“我在”、告诉大家“怎么连我”、以及每隔一会儿重复一遍。 它不描述业务端点，那是 SEDP 的活。

5.1 什么时候发、发给谁

启动时

5.4 收到 SPDP 之后做什么

  1. 校验必填项：协议版本（major 必须是 2）、participant GUID、租约、内置端点集、 metatraffic 单播 locator（UDP 或 TCP locator 都算）。缺一个就丢弃，不当半个 participant 用。
  2. 查通讯录：按 GUID prefix 找远端槽位。 没有就新建（满了就淘汰“最久没说话”的那个），有就更新。
  3. 刷新租约：记住 now，租约取对方通告的值，夹在 1 s – 1 h 之间。 对方没写租约就用本端配置的默认值。
  4. 发给对方我的名片：如果是新认识 / 对方单播地址变了， 立刻把所有本地端点用 SEDP 单播给它（不等它来问）。
  5. 立刻断言一次 liveliness：新 peer 没有历史，早点发一次免得租约马上到期。
  6. 建立 TCP（如启用）：按需拨号。

5.5 租约到期：没有“再见”

SPDP 没有 BYE / 下线报文。participant 消失只有一种表现：不再发 SPDP。 所以接收方每 200 ms 扫一遍通讯录，谁的 now - last_seen > lease， 就把这个 participant 连同它通告过的所有端点一起删掉。 

  t=0     A -> SPDP      B: last_seen = 0
  t=3s    A -> SPDP      B: last_seen = 3000
  t=6s    A -> SPDP      B: last_seen = 6000
  t=9s    A dies
  t=27s                  B: 27000 - 6000 > 20000  ->  drop A and its endpoints
为什么默认租约是 20 秒而不是 6 秒 至少要容忍连续丢几个 SPDP。3 秒一次、租约 20 秒，等于允许连丢 6 个还不误判。 租约调小会让“对方进程卡一下”变成“对方掉线”，很危险。

6. SEDP：交换名片

SPDP 只解决了“知道有这个人”。SEDP 才解决“他有哪些 writer / reader、分别是什么 topic、什么 QoS”。

6.1 两对内置端点

6.2 什么时候发

  • 新 participant 出现：把本地所有端点逐个单播给它（“证件照回放”）。
  • 本地新建端点：立刻广播给所有已知 remote。
  • 本地删除端点：发一条 dispose（K 标志、D 清 0），让对方摘掉。
  • 周期性心跳：默认每 1000 ms 给每个 remote 发 HEARTBEAT，兜底重传。 历史为空也会发（firstSN = lastSN + 1），让对方知道“我这里没有你要等的号”，从而把窗口推进过去。

6.5 删除端点（dispose）

删除不是“发个空包”。本实现会：

  1. 打包一个 key-only 的 ParameterList：只含 PID_ENDPOINT_GUID， 不再带 topic/type/QoS。
  2. 用 K=1、D=0 的 DATA 发出去，并在内联 QoS 里带 PID_STATUS_INFO = 0x00000001（disposed），然后写进 SEDP 历史。 这个状态位是必须的：没有它，Cyclone 会把样本当成一次“还活着”的重复通告， 端点永远删不掉。
  3. 接收方按 key 找到对应端点，删掉，并上报“端点移除 + 匹配数减少”。

这样即使对方当时不在线，下次心跳/重传时也能补上这条“讣告”。

6.6 SEDP 的可靠机制

SEDP 是“可靠”的（reliable），但实现得很朴素，没有 per-reader 状态：

  1. writer 把每个端点通告按序列号存进历史（容量按本地端点数分配，默认上限 1024 条；总字节预算 256 KiB）。
  2. 每 1 s 给每个 remote 发 HEARTBEAT，告诉对方“我有 firstSN..lastSN”。
  3. reader 比对 next_expected，把缺的号用 ACKNACK 位图报回去。
  4. writer 收到 ACKNACK，从历史里重发缺失的样本；已经被淘汰的用 GAP 告诉对方“别等了”。
为什么“不是 per-reader 状态”也能工作 重传是直接回给“发 ACKNACK 的那个地址”的，不做广播。 所以同一个 writer 面对多个 reader 时，各自报自己的缺口，互不干扰。 代价是：没法针对某个 reader 精确地只重传它要的，遇到重复 ACKNACK 还得靠最小间隔（10 ms）压住。

7. QoS：能不能聊得来

QoS（Quality of Service）听起来玄，其实就是两组声明：

  • writer 说“我保证做到什么”（offered，我提供多少）；
  • reader 说“我要求你做到什么”（requested，我要多少）。

匹配规则一句话：writer 提供的能力必须大于等于 reader 提出的要求。 达不到就不匹配，双方各上报一个“QoS 不兼容”事件，数据一条也不会发。

方向别搞反 是“发布者满足订阅者”，不是反过来。一个 BEST_EFFORT 的 writer 配一个 RELIABLE 的 reader， 永远匹配不上——哪怕发布者觉得自己已经尽力了。

7.2 匹配的实际顺序

代码里是“一票否决”式检查，顺序如下，返回第一个不匹配的原因：

  1. topic：话题名必须完全相同（区分大小写）。
  2. type：类型名必须完全相同。
  3. partition：分区名列表至少有一对能匹配（支持星号通配）。
  4. reliability：见上表。
  5. durability：writer 不能比 reader 弱。
  6. deadline：reader 要求了，writer 得给得起。
  7. latency budget：writer 的预算不能比 reader 要求的更宽松。
  8. ownership：必须一致。
  9. liveliness kind：AUTOMATIC 低于 MANUAL_BY_PARTICIPANT，后者低于 MANUAL_BY_TOPIC。
  10. liveliness lease：reader 要求了，writer 的租约不能更大。
  11. destination order：writer 不能比 reader 弱。
  12. presentation scope：writer 的作用域不能更小。
  13. coherent access / ordered access：reader 要，writer 就得有。

7.3 不匹配会发生什么

不会报错退出，也不会自动重试。双方各自收到一个状态事件，reason 字段就是上面那些短词： 

kind      = NB_RTPS_STATUS_QOS_INCOMPATIBLE
endpoint  = 本地端点 GUID
writer    = 对端端点 GUID
reason    = "topic" / "reliability" / "durability" / ...
has_peer  = 1

同一个不兼容对只会报一次（重复的 SEDP 刷新不会刷屏）；如果它曾经匹配上过， 后来又不兼容了，就不会再报“不兼容”，而是走“匹配数减少”的通知。

7.5 最常见的三个坑

  1. 类型名对不上：DDS 里 type name 是字符串，带不带命名空间都算不同。 抓包看 PID_TYPE_NAME 的实际值，别只看代码里的 struct 名。
  2. 以为“没写 PID = 不匹配”：没写就是默认值。默认 deadline 是无限，所以 “reader 要求 200 ms、writer 什么都没写”才是不匹配。
  3. durability 影响晚加入者能否拿到旧数据：TRANSIENT_LOCAL（及更强）的可靠 writer 会保留业务数据历史，并在发现新 reader 时主动回放（受历史深度和 256 KiB 预算限制）； VOLATILE reader 则不要求匹配前的历史。实时数据不受 durability 影响。

8.2 writer 这边：历史缓存

  • 默认深度 8 个样本（配置 data_history_depth，最大 1024）。
  • 总字节预算 256 KiB，超了就从最老的开始丢，不管深度还剩多少。
  • 被丢掉但 reader 还在问的样本，回一个 GAP，别让它一直等。
  • 每次 ACKNACK 最多重发 64 个样本，剩下的下一轮再说（防止一次把链路打满）。
  • 同一个 writer 两次重发至少间隔 10 ms（限流窗按“该 writer 最近一次请求的 reader”记录；ACKNACK 与 NACK_FRAG 共用这个窗口）。

8.3 reader 这边：窗口加位图

每个“远端 writer + 本地 reader”组合维护一个小窗口：

  • next_expected：下一个想收的序列号。
  • 一个最多 256 位的位图：记录 next_expected 之后哪些已经收到。

收到 HEARTBEAT 后，reader 这样构造 ACKNACK：

  • base 取 next_expected；
  • numBits 取 lastSN - base + 1，最多 256；
  • 位图里，base + i 没收到就把第 i 位置 1（bit0 是 0x80000000）；
  • count 是本读者的 ACKNACK 计数器，加一。

几个细节：

  • 同一个 count 的重复心跳不再应答（避免心跳风暴）。
  • 两次 ACKNACK 至少间隔 20 ms。
  • 如果 firstSN 大于 next_expected，说明中间被 writer 淘汰了，窗口直接跳到 firstSN。
  • 对方进程重启会换 GUID prefix，因此在本实现眼里是一个新的 writer，窗口会重新建立； 同一 GUID 内序号整体倒退不会自动复位（SEDP 内置 writer 另有一个 “lastSN + 1 < next_expected 就复位”的兜底，用户数据不走这条）。

8.6 可靠性的边界

“可靠”不等于“持久” 可靠只保证在一次会话内、在历史窗口里补发。以下情况仍然会丢：
  • 样本已经被历史淘汰（超过深度或 256 KiB）。
  • writer 进程重启，历史清零。
  • reader 晚于 writer 启动，且 reader 是 VOLATILE（不要历史）或 writer 是 VOLATILE（不保留历史）。
  • 读者一直不在线，超过历史窗口后再上线。

9. 一条数据的完整旅程

9.1 发送侧

  1. nb_rtps_participant_publish() 拿到 writer 的 GUID 和载荷。
  2. 查本地的 writer 端点，确认它还活着、QoS 允许。
  3. 序列号加一（每个 writer 独立计数）。
  4. 如果是可靠 writer，先把样本写进历史（带时间戳、实例句柄）。
  5. 找出所有匹配的远端 reader（数量上限由 max_remote_endpoints 决定，默认 4096）； 每个 reader 最多向 16 个单播地址（多网卡）各发一份。
  6. 对每个目标单独构造一个 DATA：
    • readerId 填对方的实体 ID，不是 0；
    • writerId 填自己的实体 ID；
    • 前面加 INFO_TS，必要时加 INFO_DST；
    • 载荷不超过 1200 就发 DATA，否则走 DATA_FRAG。

所以“一次发布”在网上可能是 1 个包，也可能是 N 个包（每个订阅者一个）。

9.2 接收侧

  1. 拆消息头，逐个子消息走。
  2. INFO_TS：记住时间戳，给后面的 DATA 用。
  3. INFO_DST：记录目标前缀；后续 Entity Submessage 不是发给本 participant 就丢弃，全 0 视为广播。
  4. DATA：看 readerId，是全 0 或自己的实体才处理。
  5. 找匹配的本地 reader：topic、type、QoS 都要过（和 SEDP 匹配用的是同一套规则）。
  6. 可靠 reader 用 256 位窗口去重；样本按到达顺序交付（不做全局重排），best effort 直接交付。
  7. 解析内联 QoS：PID_KEY_HASH（实例句柄）、PID_STATUS_INFO（dispose / unregister）。
  8. 回调业务层，附带 SampleInfo（时间戳、实例状态、序号）。

9.3 实例（key）相关的三个概念

概念线上表现含义
key hash内联 QoS 里的 PID_KEY_HASH（16B）这条数据属于哪个实例。同一实例的多条数据共享一个句柄。
disposePID_STATUS_INFO 大端值等于 0x00000001（线上最后一个字节是 01）实例被删除，但 writer 还在。
unregisterPID_STATUS_INFO 大端值等于 0x00000002（线上最后一个字节是 02）writer 不再负责这个实例。

本实现只有在业务层传了实例句柄时才写这些字段；无 key 的 topic 不会出现。

10.3 端点的一生

  create endpoint
    -> write into local table, sequence number + 1
       -> unicast SEDP DATA to every known remote
          -> peer parses, creates remote endpoint, runs QoS matching
             -> match     : MATCHED event, data may flow
             -> mismatch  : QOS_INCOMPATIBLE event (no auto retry)

  delete endpoint
    -> send dispose (K=1, D=0)
       -> peer drops remote endpoint, MATCHED event with lower count

  peer process dies
    -> lease expires (sweep every 200 ms)
       -> drop participant and all its endpoints, notify application

11.2 和 Cyclone DDS 互通时注意

  • Cyclone 只通告非默认的 QoS，并会带一些厂商 PID（例如 0x800c）； 解析时必须按长度跳过不认识的 PID，不能因此丢弃整张名片（本实现已这样做）。
  • Cyclone 要求 SPDP 里同时有 metatraffic 单播 locator 和 default unicast locator （0x0031），缺一个就不建 proxy participant（本实现默认会补上）。

12.3 手工解析一个包的顺序

  1. 前 4 字节是不是 52 54 50 53？不是就别当 RTPS 解。
  2. 第 4、5 字节是版本；第 8 到 19 字节是 guidPrefix。
  3. 从偏移 20 开始循环：读 id、flags、长度，跳到下一个。
  4. 遇到 DATA（0x15）：先看 flags 的 Q 和 D，再按第 3.5 节的偏移取 readerId、writerId、SN。
  5. 载荷开头是 00 03 00 00 就跳过 4 字节，然后按 PID 逐个读。
  6. PID_SENTINEL（0x0001）结束；长度字段一定是 4 的倍数。
